A game data declaration is a change to a game [bin file](/reference/file-formats/bin/) that you
write in the manifest of a layer. The overlay build applies the change to the game's copy of the
bin, so your mod ships no copy of the file. Objects and properties that you do not change keep the
values of the installed game.

This guide shows how to write a manifest by hand. LTK Editor writes the same file when you edit a
game bin. See [Game data declarations](/editor/bin-editor/game-data/). For every rule of the
format, see the [Game data declarations reference](/reference/mod-packages/game-data/).

:::note[Tool support]
A manifest requires a packer and an overlay build with declaration support. An LTK Manager release
applies the rules of the `ltk_game_data` version that it bundles. That version fails on a key, a
sign or a type name that it does not define.
:::

## Add your first link

Start with an existing [mod project](/making-mods/mod-projects/) and a companion bin that the game
must load. This example uses `mods/teemo-example/particles.bin` as the game path of the companion
bin. Replace it with the path of your own bin.

Put the companion bin in the WAD content of the layer, and create `game_data.yaml` in the layer
directory:

{/* prettier-ignore */}
<FileTree>
- my-mod/
  - mod.config.json
  - content/
    - base/
      - game_data.yaml
      - Teemo.wad.client/
        - mods/
          - teemo-example/
            - particles.bin
</FileTree>

```yaml title="content/base/game_data.yaml"
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    links:
      - mods/teemo-example/particles.bin
```

| Part         | Meaning                                                                  |
| ------------ | ------------------------------------------------------------------------ |
| `version: 1` | The version of the declaration format. It is not the League patch number |
| `modules`    | The ordered list of modules of this layer                                |
| `target`     | The game chunk that the module edits                                     |
| `links`      | The dependency paths that the module adds to the target                  |

- The target must exist in the game or in enabled mod content. Your project needs no copy of
  `skin0.bin`.
- The companion `particles.bin` must exist at the declared path in content that the game loads.
- A link does not create the companion bin, and it does not copy the objects of that bin into the
  target.
- A link does not redirect a particle effect to an object in the companion bin. To redirect an
  effect, [edit the properties of an entry](#edit-an-entrys-properties).

## Choose a target

`target` is one string: a game path or a WAD chunk hash.

| Example value                           | Meaning                                                           |
| --------------------------------------- | ----------------------------------------------------------------- |
| `data/characters/teemo/skins/skin0.bin` | A game path                                                       |
| `shared`                                | A game path with no extension                                     |
| `'0123456789abcdef'`                    | A chunk hash of exactly 16 hexadecimal digits, here a placeholder |

- Write the chunk path as it is inside the WAD. Omit `content/base/`, the WAD directory name and
  any absolute file system prefix.
- Keep the extension of the chunk. Write no extension for a chunk that has none.
- Use forward slashes, including on Windows.
- A hash has no `0x` prefix and no `.bin` suffix. The loader reads a string with either as a path.
- Quote a hash in YAML. YAML reads a hash that contains only digits as a number.
- The build matches a path ASCII case-insensitively. The loader does not change the path: a
  separator, a space and a suffix stay as written.
- `target: { path: ... }` and `target: { hash: ... }` are errors.

A link value is a game path of 1 to 65,535 UTF-8 bytes. It is not a hash, and it is not the name
of a local file.

### Select by entry name

Use `entries` to select a bin by an entry that it declares. The build resolves the name through
the game index to each **declaring chunk**: a game bin that contains the entry.

```yaml
version: 1
modules:
  - entries:
      Characters/Teemo/Skins/Skin0:
        links:
          - mods/teemo-example/particles.bin
```

- The build adds the link to the dependency list of each declaring chunk.
- An entry body under `entries` accepts [property edits](#edit-an-entrys-properties) and the keys
  `links`, `+links` and `-links`.
- An entry key is an object path or an object hash: `0x` followed by exactly 8 hexadecimal digits.
  Quote a hash in YAML, for example `'0xd2343ed1'`.
- The build matches an object path ASCII case-insensitively. The manifest and the diagnostics keep
  the casing that you write.
- An `entries` module contains only the entry mapping and an optional `name`. `target`, `edits`
  and `source` are errors in it.
- The build applies the entries in mapping order. To apply two edits to one entry in order, write
  two modules.

The build does not fail in these cases:

| Diagnostic         | Cause                                                 | Result                                 |
| ------------------ | ----------------------------------------------------- | -------------------------------------- |
| `EntryFanOut`      | Several chunks declare the entry                      | The build edits each chunk             |
| `EntryUnresolved`  | No game bin declares the entry                        | The build skips the edits of the entry |
| `IndexUnavailable` | The build can neither load nor build the object index | The build skips each `entries` module  |

## Add and remove dependencies

Use `links` or `+links` to add a dependency. Both keys have the same meaning. Use `-links` to
remove a dependency. This manifest removes one dependency and adds another:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    -links:
      - mods/teemo-example/old-particles.bin
    +links:
      - mods/teemo-example/particles.bin
```

- `links` adds to the list. It does not replace the list.
- The build compares paths ASCII case-insensitively.
- An addition keeps its written casing and its position in the list. The build omits a path that
  the list already contains.
- If the list does not contain the path of a removal, the build reports `LinkRemovalUnmatched` and
  applies the other edits.
- In one edit, the build applies removals before additions, in any key order. An edit that removes
  and adds the same path leaves the path in the list.
- An edit can contain `links` or `+links`, not both.
- In a `target` module, write `links` beside the entry names. Under an entry name of a `target`
  module, `links` is a property path.

## Edit an entry's properties

An entry name beside `target` starts an entry body. Each key of the body is a property path, with
an optional sign in front. Each value is the new value of the property. This example sets a
texture and a lighting value, adds one audio tag, removes another, and changes two resource slots:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    Characters/Teemo/Skins/Skin0:
      skinMeshProperties.selfIllumination: 1.0
      skinMeshProperties.texture: assets/characters/jade_teemo/skins/base/jade_teemo_base_tx_cm.tex
      skinAudioProperties:
        +tagEventList: [Jade_Teemo]
        -tagEventList: [Teemo]
    Characters/Teemo/Skins/Skin0/Resources:
      -resourceMap: [Teemo_R_Firefly_GroundLight]
      +resourceMap:
        Teemo_R_Mis: Characters/Jade_Teemo/Skins/Skin0/Particles/Jade_Teemo_Base_R_Mis
```

| Part                                  | Meaning                                                                             |
| ------------------------------------- | ----------------------------------------------------------------------------------- |
| `Characters/Teemo/Skins/Skin0`        | The entry to edit. An entry name in a `target` module has a slash or is a `0x` hash |
| `skinMeshProperties.selfIllumination` | A dotted path to a field of a struct. The value replaces the value of the game      |
| `skinAudioProperties:` with a block   | The same struct as a block. Each key in the block is a path relative to the struct  |
| `+tagEventList`                       | Adds the elements to the list. On a map, adds or replaces the keys                  |
| `-tagEventList`, `-resourceMap`       | Removes the elements from the list, or the keys from the map                        |

Copy entry names and property names from the bin that you inspect. An entry name is not derived
from the file name of the bin.

The same body is valid under `entries`. The build then edits the entry in each declaring chunk:

```yaml
version: 1
modules:
  - entries:
      Characters/Teemo/Skins/Skin0:
        skinMeshProperties.selfIllumination: 1.0
        links:
          - mods/teemo-example/particles.bin
```

### Values

Write a value as plain YAML: `1.0` is a number, `true` is a boolean, and a game path is a string.
The build reads the type of the property from the schema of the installed patch and converts the
value to it:

- The build hashes a string on a `hash` or `link` property.
- The build hashes a string on a `file` property as a path.
- A list of numbers on a `vec3` property is a vector.

If the schema has no type for a property, the build uses the type of the value in the game's bin
and reports `SchemaFallback`, which is informational. If the game's bin omits the property and no
type is known, the build skips the key.

### Signs

- A key with no sign sets the value. On a list or a map, it replaces the whole container.
- `+` adds elements to a list, and adds or replaces keys of a map. The other elements and keys
  stay.
- `-` removes elements from a list, and keys from a map. On a list of structs, `-` takes indexes.
- A sign is valid on a list or a map property only. On any other property, the build skips the
  key.
- If a removal matches no element or key, the build skips the key.
- For one key, the build applies the set first, then the removals, then the additions. If one of
  them fails, the build skips all three for that key and applies the other keys.

### Blocks and dotted paths

The dotted form and the block form are the same edit. A block on a struct changes the fields that
are keys of the block, and the other fields keep their values. Use one form for a field in an
entry body. If both forms set one field, the build applies the later value.

### Type pins

A **type pin** requires one type for a value. In YAML it is a tag in front of the value:
`selfIllumination: !f32 1.0`. In TOML and JSON it is a mapping with one key: `{ f32 = 1.0 }`.

- If the property has another type, the build skips the key.
- A pin does not supply a type. If no type is known for the property, the build skips the key with
  or without a pin.
- A block whose only key is a type name, such as `hash`, is a pin. To set a field with that name,
  write the dotted path.
- A `pointer` pin constructs a struct where the game's bin has a null pointer. Write the class in
  parentheses and the fields under it: `!pointer(SomeClass) { field: 1 }`.
- The YAML loader fails on the tag `!bool`. Write `{ bool: false }`, or write the value with no
  pin.

The reference lists the [type names](/reference/mod-packages/game-data/#type-pins) and the
[conversion table](/reference/mod-packages/game-data/#coercion).

### References

A **reference** is a value that the build reads from the installed game. Write it as
`<entry name>:<property path>`. In YAML:
`texture: !ref Characters/Ahri/Skins/Skin0:skinMeshProperties.texture`. In TOML and JSON:
`{ ref = "Characters/Ahri/Skins/Skin0:skinMeshProperties.texture" }`.

- Use a reference in place of a value that you copy from a bin. A copied value keeps the value of
  the patch that you read it from. The build reads a reference again on every build.
- The build resolves a reference against the game's own copy and never against the edits of a mod.
  The enabled mods and their order do not change the result.

See [References](/reference/mod-packages/game-data/#references) in the reference for the form and
the diagnostics.

## Create, clone and remove objects

`objects` in a `target` module creates and removes objects of the target bin. Each key is the name
of an object. Name a new object under `Mods/<modid>/` to keep its name different from the names of
game objects.

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    objects:
      # A copy of a game object, with one property changed.
      Mods/TeemoExample/Particles/R_Missile:
        clone: Characters/Teemo/Skins/Skin0/Particles/Teemo_Base_R_Mis
        set:
          particleName: Teemo_Example_R_Mis

      # A new object of a class.
      Mods/TeemoExample/Resources:
        class: ResourceResolver
        set:
          resourceMap:
            Teemo_R_Mis: Mods/TeemoExample/Particles/R_Missile

      # An object to delete.
      Characters/Teemo/Skins/Skin0/Particles/Teemo_Base_R_Firefly_GroundLight:
        remove: true
```

| Body                            | Result                                                             |
| ------------------------------- | ------------------------------------------------------------------ |
| `clone` with an optional `set`  | A copy of an entry of the target, with the `set` applied           |
| `class` with an optional `set`  | An object of that class that contains only the properties in `set` |
| `remove: true` and no other key | The build removes the object                                       |

- `set` is an entry body. It accepts the same paths, signs, blocks, pins and references as
  [the body of an entry](#edit-an-entrys-properties).
- A clone copies the class and the properties of its source. The build also rewrites the property
  that contains the path of the source, such as `objectPath` or `particlePath`, to the new name.
- The game supplies the class defaults for each property that a constructed object omits.
- The game does not read a new object until a `link` property or a resource slot refers to it. Set
  a `link` property or a resource slot to the new name.
- `objects` is an error in an `entries` module.

In YAML, a constructed object has a shorter form. Write the class as a tag on the object, and the
properties directly under it:

```yaml
objects:
  Mods/TeemoExample/Resources: !ResourceResolver
    resourceMap:
      Teemo_R_Mis: Mods/TeemoExample/Particles/R_Missile
```

The loader reads this body as the `class` and `set` body above. A clone and a removal have no tag
form. TOML and JSON have no tags.

A clone reads the bin as it is before the build creates the objects of the same edit. To clone an
object that you create, put the second clone in a later item of an `edits` list:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    edits:
      - objects:
          Mods/TeemoExample/Particles/R_Missile:
            clone: Characters/Teemo/Skins/Skin0/Particles/Teemo_Base_R_Mis

      - objects:
          Mods/TeemoExample/Particles/R_Missile_Extra:
            clone: Mods/TeemoExample/Particles/R_Missile
```

If an object edit does not apply, the build reports `ObjectSkipped` with one of these reasons:

| Reason             | Cause                                                   |
| ------------------ | ------------------------------------------------------- |
| `objectExists`     | The target already contains an object with the new name |
| `sourceMissing`    | The target does not contain the clone source            |
| `unknownClass`     | The schema does not define the class                    |
| `removalUnmatched` | The target does not contain the object to remove        |

`ObjectShadowsGame` is informational: another game bin declares an object with the new name. The
build still creates the object.

## Apply an override file

`overrides` applies `.ptch` files of the layer to the target. A `.ptch` file is a `PTCH` bin with
property records. Use it for an edit that the build must apply exactly as written: the build
converts no value of a record.

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    overrides:
      - teemo-skin0.ptch
```

- The loader resolves the path against the layer directory, or against the directory of the source
  file that contains it.
- `overrides` is valid only in a `target` module.
- A `.rito` path is an error.
- In one edit, the build applies override files before objects, entries and links.

## Organize edits into modules

A **module** selects a chunk with `target`, or entries with `entries`. A `target` module has one
of these forms:

- Bindings beside `target`, such as the `links` list in the first example
- An `edits` list of ordered edits
- A `source` path of a file that contains the bindings or the edits

An `entries` module contains only its entry mapping and an optional `name`.

Use `edits` when the build must apply one edit to the result of another. In this example, the
second edit removes the link that the first edit adds. The resulting list has no `temporary.bin`:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    edits:
      - links:
          - mods/teemo-example/temporary.bin
      - -links:
          - mods/teemo-example/temporary.bin
```

- The build applies modules in list order, each to the result of the module before it.
- Two modules can have the same `target`.
- To edit another bin, add a module with another `target`.
- A module takes an optional `name`, a label that LTK Editor shows in the **Declarations** view.
  A name does not change the build.

```yaml
version: 1
modules:
  - name: Example particles
    target: data/characters/teemo/skins/skin0.bin
    links:
      - mods/teemo-example/particles.bin
```

## Reuse a source file

A source file contains a body with no target. A module in the manifest assigns it to a target:

{/* prettier-ignore */}
<FileTree>
- content/base/
  - game_data.yaml
  - declarations/
    - particle-links.yaml
</FileTree>

```yaml title="content/base/game_data.yaml"
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    source: declarations/particle-links.yaml
```

```yaml title="content/base/declarations/particle-links.yaml"
version: 1
links:
  - mods/teemo-example/particles.bin
```

- Keep `target` in the manifest. The source file contains its own `version: 1` and bindings or
  `edits`. `modules`, `target`, `name` and `source` are errors in a source file.
- The `source` path is relative to the layer directory, here `content/base/`. Use forward slashes.
  The path must resolve to a file inside the layer directory, after the loader resolves symlinks.
- A source file can be YAML, TOML or JSON. Its format is independent of the format of the
  manifest.
- To use the edit on another target, add a module with the same `source`. A manifest that assigns
  one source file to one target twice is an error.
- To change the result of a source file, add a module for the same target after the module with
  `source`. A module with `source` can contain no other binding.
- The manifest and each referenced source file must exist, and `.modignore` must not exclude them.
- A file that no manifest references adds no declaration.

## Choose a manifest format

A layer accepts one manifest: `game_data.yaml`, `game_data.yml`, `game_data.json` or
`game_data.toml`. Two manifests in one layer are an error.

<Tabs>
  <TabItem label="YAML">

    ```yaml title="content/base/game_data.yaml"
    version: 1
    modules:
      - target: data/characters/teemo/skins/skin0.bin
        links:
          - mods/teemo-example/particles.bin
    ```

  </TabItem>
  <TabItem label="JSON">

    ```json title="content/base/game_data.json"
    {
      "version": 1,
      "modules": [
        {
          "target": "data/characters/teemo/skins/skin0.bin",
          "links": ["mods/teemo-example/particles.bin"]
        }
      ]
    }
    ```

  </TabItem>
  <TabItem label="TOML">

    ```toml title="content/base/game_data.toml"
    version = 1

    [[modules]]
    target = "data/characters/teemo/skins/skin0.bin"
    links = ["mods/teemo-example/particles.bin"]
    ```

  </TabItem>
</Tabs>

A manifest contains one `version` and one `modules` list. An unknown key, a duplicate key, an
unsupported version and a module with two body forms are errors.

YAML has comments, tags and nested blocks. Follow these rules in a YAML manifest:

- Indent with two spaces at each level. Do not use tabs.
- Quote a hash: `'0xd2343ed1'`. YAML reads `0xd2343ed1` without quotes as a number.
- Quote a key that contains a map subscript: `'resourceMap{"Teemo_R_Mis"}'`.
- Write `1.0` for a number, `true` for a boolean and `'1.0'` for a string.
- Write a short vector in brackets: `[50.0, 180.0, 150.0]`.
- Write each mapping key once. To write a property twice in order, use two modules or two edits.

## Layers, order and packaging

Each layer has its own manifest. Only enabled layers add declarations. `mod.config.json` and
`mod.config.toml` do not list declaration files.

The build takes the **base** of a target from the enabled mod with the highest precedence that
ships a copy of the chunk. If no mod ships a copy, the base is the game's copy. The build applies
declarations in this order:

1. Mods, from the lowest precedence to the highest
2. Layers of a mod: the base layer first, then the other layers from the lowest priority to the
   highest, and layers with the same priority in name order
3. Modules, in manifest order
4. Edits, in list order

- File names of source files do not change the order.
- A removal in a mod with a higher precedence can remove an addition of a mod with a lower
  precedence.
- A whole-file copy of a bin in a mod is the base for every declaration on that bin.

[Packing](/making-mods/packaging/) validates the manifest and expands each source file into the
package metadata. The manifest, the source files and the override files are build resources, and
packing excludes them from game content. Packing fails on an invalid declaration. Checks that need
the game, such as the existence of a target, run in the overlay build.

- A `.modpkg` stores the declarations of each layer.
- A `.fantome` stores them in the LeagueToolkit extension of `META/info.json`. A tool with no
  support for the extension installs the mod without the declarations.
- Extraction writes a `game_data.json` manifest that contains the body of every module and uses no
  source file. It keeps module order, module names and the order of an `entries` mapping. It does
  not restore source file names, comments or formatting.

## Check the result

Build the overlay with the intended mods and layers enabled, then read its diagnostics. A
successful pack validates the declaration files. It does not check that each target and each
dependency exists in the game. A target must be a `PROP` bin of version 2 or 3, or a `PTCH` bin.

| Problem                          | What to do                                                                                                                                                                  |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Several manifests                | Keep one `game_data.*` manifest in the layer directory.                                                                                                                     |
| `DeclarationsRejected`           | Read the reported file, key, `version` and module form. The build skips the declarations of a layer that contains an invalid module. It keeps the other content of the mod. |
| A YAML duplicate key error       | Put the fields under one entry block, or use separate modules or edits for ordered writes.                                                                                  |
| A missing or ignored source file | Compare the `source` path with the file name, and check `.modignore`.                                                                                                       |
| A duplicate source assignment    | Assign a source file to a target once.                                                                                                                                      |
| A rejected module with `source`  | Keep only the `target` and the `source` in that module. Put other bindings in the next module.                                                                              |
| A target rejected as a mapping   | Write `target` as one string: a path, or a quoted hash of 16 digits.                                                                                                        |
| `TargetSkipped`                  | Check the game path or the hash, the enabled content and the bin format.                                                                                                    |
| `NoEffect`                       | No edit of the module changed the target. Read the other diagnostics of that module.                                                                                        |
| `EntryUnresolved`                | Check the entry name or the `0x` hash against the installed game. No game bin declares it.                                                                                  |
| `EntryFanOut`                    | Informational. Several chunks declare the entry, and the build edits each one.                                                                                              |
| `IndexUnavailable`               | Read the object index error in the build log.                                                                                                                               |
| `PropertyEditSkipped`            | One property key did not apply. The diagnostic contains the entry name, the signed key and a reason code. Check the key against the class of the entry in the schema.       |
| `pinMismatch` on a struct block  | The only key of the block is a type name, so the block is a [type pin](#type-pins). Write the field as a dotted path.                                                       |
| `SchemaFallback`                 | Informational. The schema has no type for the property, and the build used the type of the game's value or the fallback type of the schema.                                 |
| `ObjectSkipped`                  | Check the reason code under [Create, clone and remove objects](#create-clone-and-remove-objects).                                                                           |
| `LinkRemovalUnmatched`           | The list does not contain the dependency when the build applies that edit. Check the path and the edits before it.                                                          |
| A missing linked bin             | Supply the companion bin at the declared game path in enabled content.                                                                                                      |
| No edit applies                  | Check that the layer is enabled, that the manifest is in the layer directory, and that the packer and the overlay build support declarations.                               |

The reference lists every [diagnostic and reason code](/reference/mod-packages/game-data/#diagnostics).
