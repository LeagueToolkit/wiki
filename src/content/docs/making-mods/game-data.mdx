Game data declarations describe edits to a game's [BIN file](/reference/file-formats/bin/).
You write them in a layer manifest. The overlay builder applies them to the target BIN while
building your mod's overlay.

This guide covers **links**, the dependency paths in a BIN's header, and **property edits**,
values you set, add, or remove on an entry of the BIN. You can add a companion BIN to the
dependency list, remove an existing dependency, and change the properties of an entry the BIN
declares. Objects and properties you do not name stay intact.

:::caution[Tool support]
These examples require a packer and overlay builder with the declaration support in
[league-mod#225](https://github.com/LeagueToolkit/league-mod/pull/225).
Support in a particular LTK Manager release depends on its bundled engine. This guide describes
hand-authored project files; it does not require a declaration editor in the Workshop.
The `entries` selector requires the game-index support in
[league-mod#228](https://github.com/LeagueToolkit/league-mod/issues/228).

The supported bindings are `links`, `+links`, `-links`, `overrides` with `.ptch` files
([league-mod#191](https://github.com/LeagueToolkit/league-mod/issues/191)), and entry bodies of
property edits under an entry name ([league-mod#243](https://github.com/LeagueToolkit/league-mod/issues/243),
[league-mod#244](https://github.com/LeagueToolkit/league-mod/issues/244)): signed keys, block
nesting, type pins, and references
([league-mod#264](https://github.com/LeagueToolkit/league-mod/pull/264)) as the
[reference](/reference/mod-packages/game-data/#entries) describes
them. A `.rito` override file is refused with an error naming the extension. `objects` and
`modes` belong to the broader [proposal](/reference/mod-packages/game-data/); the engine rejects
those bindings.
:::

## Add your first link

Start with an existing [mod project](/making-mods/mod-projects/) and a companion BIN you want
the game to load. This example uses `mods/teemo-example/particles.bin` as your custom BIN's
game path. Replace it with the path of your own content.

Place the companion BIN in the layer's WAD content and create `game_data.yaml` at the layer root:

{/* prettier-ignore */}
<FileTree>
- my-mod/
  - mod.config.json
  - content/
    - base/
      - game_data.yaml
      - Teemo.wad.client/
        - mods/
          - teemo-example/
            - particles.bin
</FileTree>

`content/base/game_data.yaml`:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    links:
      - mods/teemo-example/particles.bin
```

| Part         | Meaning                                                                 |
| ------------ | ----------------------------------------------------------------------- |
| `version: 1` | The declaration format version, independent of the League patch number. |
| `modules`    | An ordered list of edits in this layer.                                 |
| `target`     | The game chunk to edit.                                                 |
| `links`      | Dependency paths to add to that target.                                 |

The target must exist in the game or enabled mod content. You do not need a copy of
`skin0.bin` in this project for a link edit. The companion `particles.bin` must exist at the
declared path in content available to the game.

Adding a link does not create the companion BIN, copy its objects into the target, or redirect
a particle effect to an object inside it. Those are separate content changes.

## Choose a target

`target` is one string, containing either a game path or a raw WAD chunk hash:

| Example value                           | Interpretation                                                                 |
| --------------------------------------- | ------------------------------------------------------------------------------ |
| `data/characters/teemo/skins/skin0.bin` | A literal game path.                                                           |
| `shared`                                | An extensionless game path.                                                    |
| `'0123456789abcdef'`                    | A raw hash: exactly 16 hexadecimal digits. This example hash is a placeholder. |

Use the chunk path inside the WAD. Leave out `content/base/`, the WAD directory name, and any
absolute filesystem prefix. Preserve the actual extension, including its absence. Use forward
slashes, including on Windows.

Raw hashes have no `0x` prefix or `.bin` suffix. A string with either is treated as a path.
Always quote hashes in YAML, especially values containing only digits. A literal path consisting
of exactly 16 hexadecimal characters is reserved for hash notation.

Path lookup ignores ASCII letter case. Other characters remain literal: separators, whitespace,
and suffixes are not cleaned up. The object forms `target: { path: ... }` and
`target: { hash: ... }` are invalid in this engine.

Link values are game paths, not raw hashes or local source filenames. Each link is a nonempty
string of at most 65,535 UTF-8 bytes.

### Select by entry name

Use `entries` to select a BIN through an entry it declares. The game index resolves the name
to every **declaring chunk**: a game BIN that contains that entry.

```yaml
version: 1
modules:
  - entries:
      'Characters/Teemo/Skins/Skin0':
        links:
          - mods/teemo-example/particles.bin
```

The link applies to the dependency list of every declaring chunk. An entry body holds
[property edits](#edit-an-entrys-properties) beside `links`, `+links`, and `-links`; the link
keys are the link engine's extension of the standard.

An entry key is a nonempty object name or an object hash: lowercase `0x` followed by exactly
8 hexadecimal digits. The digits accept either case. Quote hashes in YAML, for example
`'0xd2343ed1'`. Object names match by FNV-1a 32 of their ASCII-lowercased spelling.
The manifest and reports keep your spelling.

Each `entries` item is one batch. It contains only the entry mapping, with no `target`,
`edits`, or `source`. Entry bodies have no `edits` or `source` either. Entries apply in
mapping order. Use separate module items for repeated edits to one entry.

Several declaring chunks produce an informational `EntryFanOut` report. The build edits every
one. A missing entry produces `EntryUnresolved` and skips that entry's edits. An unavailable
object index produces `IndexUnavailable` for each `entries` item and skips those items.
The build continues in each case.

## Add and remove dependencies

Use `links` or its alias `+links` for additions. Use `-links` for removals. This alternative
manifest removes an example old dependency and adds its replacement:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    '-links':
      - mods/teemo-example/old-particles.bin
    '+links':
      - mods/teemo-example/particles.bin
```

`links` adds to the existing list; it does not replace the list. Matching ignores ASCII letter
case. Additions preserve the written spelling and list order, with duplicate paths omitted.
A removal with no matching dependency produces a diagnostic and leaves the other edits active.

Within one edit, removals run before additions, regardless of key order. Removing and adding the
same path leaves that path present. An edit can contain `links` or `+links`, but not both aliases.

## Edit an entry's properties

An entry name under `target` opens an entry body. Each key in the body is a property path, with
an optional sign in front; each value is what the property becomes. This example gives base
Teemo one texture from a companion skin, a lighting value, one tag more and one tag less, and a
replaced particle:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    'Characters/Teemo/Skins/Skin0':
      skinMeshProperties.selfIllumination: 1.0
      skinMeshProperties.texture: assets/characters/jade_teemo/skins/base/jade_teemo_base_tx_cm.tex
      skinAudioProperties:
        '+tagEventList': [Jade_Teemo]
        '-tagEventList': [Teemo]
    'Characters/Teemo/Skins/Skin0/Resources':
      '-resourceMap': [Teemo_R_Firefly_GroundLight]
      '+resourceMap':
        Teemo_R_Mis: Characters/Jade_Teemo/Skins/Skin0/Particles/Jade_Teemo_Base_R_Mis
```

| Part                                  | Meaning                                                                                |
| ------------------------------------- | -------------------------------------------------------------------------------------- |
| `'Characters/Teemo/Skins/Skin0'`      | The entry to edit. An entry name at the module root carries a slash or is a `0x` hash. |
| `skinMeshProperties.selfIllumination` | A dotted path into a struct field. The value replaces what the base has.               |
| `skinAudioProperties:` with a block   | The same struct as a block. Each key inside is a path relative to the struct.          |
| `'+tagEventList'`                     | Add these elements to the list. On a map, add or replace these keys.                   |
| `'-tagEventList'`, `'-resourceMap'`   | Remove these elements from the list, or these keys from the map.                       |

Write values as plain YAML: `1.0` is a number, `true` is a boolean, a game path is a string.
The build reads the property's type from the installed patch's schema and converts the value to
it: a string on a `hash` or `link` property is hashed, on a `file` property it is hashed as a
path, a number list on a `vec3` property is a vector. Where the schema says nothing about a
property, the type is the one the base BIN holds, and the build reports the fallback as
informational. A property the base omits and the schema does not know is skipped.

A sign belongs on a list or map property. On a plain value it is a report, and the edit is
skipped. `-` on a list matches elements by value, or by index when the elements are structs;
on a map it matches by key. A removal that matches nothing is a report. Within one key the set
applies first, then the removals, then the additions; a report on any of the three skips that
key and the remaining keys continue.

The dotted spelling and the block spelling are the same edit. A block on a struct merges
field by field, and a field the block does not name keeps its base value. Choose one spelling
for a field within a module; both spellings together are two writes to the same property.

A **type pin** fixes the type a value must have. In YAML it is a tag in front of the value,
`selfIllumination: !f32 1.0`; in TOML and JSON it is a one-key mapping, `{ f32 = 1.0 }`. A pin
whose type disagrees with the property's is a report, and the edit is skipped. A block whose
only key is a type name, such as `hash`, is read as a pin; write that field as a dotted path. A `pointer` pin
builds a struct where the base has a null pointer, with the class in parentheses and the fields under
it: `!pointer(SomeClass) { field: 1 }`.
The [reference](/reference/mod-packages/game-data/#type-pins) lists the type names and the full
conversion table.

A **reference** names a value in the installed game instead of copying it, written
`<entry name>:<property path>`: `speed: !ref Characters/Ahri/Skins/Skin0:speed` in YAML, or
`{ ref = "Characters/Ahri/Skins/Skin0:speed" }` in TOML and JSON. Use it wherever you would
otherwise paste a number out of a bin you inspected. The copied number is frozen at the patch
you read it from and silently goes stale; the reference is re-read on every build. It reads the
game's own copy, never another mod's edits, so the result never depends on which mods are
enabled or in what order. The
[reference](/reference/mod-packages/game-data/#references) covers the spelling and the reports.

The same body works under `entries`, where the build edits the entry in every declaring chunk:

```yaml
version: 1
modules:
  - entries:
      'Characters/Teemo/Skins/Skin0':
        skinMeshProperties.selfIllumination: 1.0
        links:
          - mods/teemo-example/particles.bin
```

## Organize edits into modules and edit lists

A **module** selects a chunk with `target` or named entries with `entries`.
A `target` module contains one of these forms:

- Direct bindings, such as the `links` list in the first example.
- An `edits` list of ordered binding groups.
- A `source` filename containing the bindings or edits.

Keep one form per `target` module. An `entries` module contains only its entry mapping.
There is no `inline` wrapper.

Use `edits` when the order between groups matters. In this example, the second edit removes the
link added by the first. The final list has no `temporary.bin` dependency:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    edits:
      - links:
          - mods/teemo-example/temporary.bin
      - '-links':
          - mods/teemo-example/temporary.bin
```

You can also repeat a target in separate modules. Modules run in array order, and each module
reads the preceding module's result. Add another module with a different `target` to edit another BIN.

## Reuse a source file

A source file holds an edit independently of its target. For example:

{/* prettier-ignore */}
<FileTree>
- content/base/
  - game_data.yaml
  - declarations/
    - particle-links.yaml
</FileTree>

`content/base/game_data.yaml`:

```yaml
version: 1
modules:
  - target: data/characters/teemo/skins/skin0.bin
    source: declarations/particle-links.yaml
```

`content/base/declarations/particle-links.yaml`:

```yaml
version: 1
links:
  - mods/teemo-example/particles.bin
```

Keep `target` in the manifest. The source has its own `version: 1` and direct bindings or
`edits`; it has no `modules` wrapper. A source cannot select a target or include another source.

The `source` path is relative to the layer root, here `content/base/`. It uses forward slashes
and must stay within that layer, including through symlinks. A source may use YAML, TOML, or
JSON independently of the manifest's format.

To reuse the edit for another target, add another module referencing the same source. Assigning
the same source to the same target twice is an error. To customize a source's result, add a
separate module for that target immediately below the source module.

The manifest and referenced sources must exist and must not be excluded by `.modignore`.
An unreferenced source file contributes no declarations.

## Choose a manifest format

Each layer accepts exactly one manifest: `game_data.yaml`, `game_data.yml`, `game_data.json`, or
`game_data.toml`. Choose one of these alternatives; do not place multiple formats in the same layer.

<Tabs>
  <TabItem label="YAML">

    `content/base/game_data.yaml`:

    ```yaml
    version: 1
    modules:
      - target: data/characters/teemo/skins/skin0.bin
        links:
          - mods/teemo-example/particles.bin
    ```

  </TabItem>
  <TabItem label="JSON">

    `content/base/game_data.json`:

    ```json
    {
      "version": 1,
      "modules": [
        {
          "target": "data/characters/teemo/skins/skin0.bin",
          "links": ["mods/teemo-example/particles.bin"]
        }
      ]
    }
    ```

  </TabItem>
  <TabItem label="TOML">

    `content/base/game_data.toml`:

    ```toml
    version = 1

    [[modules]]
    target = "data/characters/teemo/skins/skin0.bin"
    links = ["mods/teemo-example/particles.bin"]
    ```

  </TabItem>
</Tabs>

Keep one `version` and one `modules` list in a manifest. Unknown fields, duplicate keys,
unsupported versions, and mixed module forms are errors.

## Layers, ordering, and packaging

Each layer owns its manifest. Only enabled layers contribute declarations. You do not list
declaration filenames in `mod.config.json` or `mod.config.toml`.

The overlay builder selects the highest-precedence enabled mod copy of the target as its base,
or the game's copy when no mod supplies one. It applies declarations in this order:

1. Mods from lowest to highest precedence.
2. Layers from lowest to highest priority, with layer name as the tie-breaker.
3. Modules in manifest order.
4. Edits in their listed order.

Source filenames do not control order. A higher-precedence removal can remove a lower-precedence
addition. A whole-file mod copy also supplies the starting objects and dependencies for all
declarations targeting that BIN.

[Packing](/making-mods/packaging/) validates the manifests and expands source files into package
metadata. These files are build inputs and are excluded from game content. Invalid declarations
fail packing. Game-dependent checks, such as target existence, happen during the overlay build.

`.modpkg` carries declarations per layer. `.fantome` carries base-layer declarations in the
LeagueToolkit extension; a consumer must support that extension to apply them. Fantome packing
omits non-base layers. Extraction reconstructs a `game_data.json` manifest with inline edits for
`target` modules and compact entry bodies for `entries` modules. Entry mapping order survives
packing and extraction. Source filenames, comments, and formatting are not reconstructed.

## Check your result

Build the overlay with the intended mods and layers enabled, then inspect its diagnostics.
A successful pack verifies the declaration files, not the availability of every game target or
dependency. The target must be a valid `PROP` BIN at version 2 or 3; `PTCH` files and version 1
BINs are unsupported bases.

| Problem                     | What to check                                                                                                                                                                                                                                                                                            |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Multiple manifests          | Keep one `game_data.*` manifest at the layer root.                                                                                                                                                                                                                                                       |
| Declarations rejected       | Check the reported file, supported keys, `version`, and module body form. An invalid module rejects that layer's declarations. Ordinary mod content remains available during overlay building.                                                                                                           |
| Missing or ignored source   | Match the layer-relative filename and check `.modignore`.                                                                                                                                                                                                                                                |
| Duplicate source assignment | Keep only one assignment of a given source to a given target, including aliases of either path.                                                                                                                                                                                                          |
| Target skipped              | Check its game path or 16-digit hash, enabled content, and BIN format. A missing, invalid, or blocked target receives no declaration edits.                                                                                                                                                              |
| `EntryUnresolved`           | Check the entry name or `0x` plus 8-digit object hash against the installed game. No game BIN declares it.                                                                                                                                                                                               |
| `EntryFanOut`               | Informational: several chunks declare the entry, and the build edits every one. Check the reported chunks.                                                                                                                                                                                               |
| `IndexUnavailable`          | Check the object-index error in the build log. The build skips every `entries` item and continues.                                                                                                                                                                                                       |
| `PropertyEditSkipped`       | One property key did not apply. The report names the entry, the signed key, and a reason code: a missing property, a sign on a plain value, a value that does not convert, a pin that disagrees with the type, or a removal that matches nothing. Check the key against the entry's class in the schema. |
| `SchemaFallback`            | Informational: the schema says nothing about the property, and the build typed it from the base BIN.                                                                                                                                                                                                     |
| Link removal is absent      | The dependency is not present at that edit. Check the path and preceding edits.                                                                                                                                                                                                                          |
| Linked BIN is missing       | Supply the companion BIN at the declared game path in enabled content.                                                                                                                                                                                                                                   |
| No edits appear             | Check the layer is enabled, the manifest is at its root, and both packing and overlay tools support declarations.                                                                                                                                                                                        |
